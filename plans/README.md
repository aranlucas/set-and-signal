## Why 001 was shipped

It is the only finding that is a substantial correctness bug and user-facing.
A single ordinary assistant call (for example "log 3×10 push-ups" via
`log_exercise_sets`, or `set_program` with an exercise that has no `sets`)
stores a record that fails the browser's strict `appStatePatch` schema. The
browser then rejects the **entire** hosted snapshot (`TrainingSync.accept`
throws "Invalid training data from Convex"), so the account stays stuck in
"Changes haven't synced" on every device. The repo's own tests can verify the
fix completely: Go unit tests cover the write paths and a convex-test case
covers the Convex backstop. Plan 002 is a hardening change that relies on
`SameSite=Lax` mitigation already being in place. Plan 003 is a low-impact
data-minimization fix. Plan 004 is a design spike.

## Dependency notes

- 004 depends on 001 because a log preview has to validate against the same

## Findings considered and rejected

- **Browser sync queue lost-update or duplicate risks** (`web/src/app/store/training-sync.ts`):
  per-record expected/value CAS, idempotent replay and persist-before-ack are
  already in place and covered by `training-sync.test.ts`. No defect found.
- **Go whole-state lost updates**: `MutateState` uses compare-and-swap on the
  profile revision with bounded retries (`internal/convex/client.go:164-190`).
  Working as designed.
- **`log_workout` annotated idempotent**: correct, because `PutWorkout` upserts
  by the required workout `id`.
- **OAuth state binding, Apple form_post, timer race, mobile restore**: fixed in
  #94 (`docs/reliability-audit.md`). Not re-audited.
- **UTC default date for `get_muscle_balance` `asOf`**: minor (the tool has no
  `tz` input). Not worth a plan by itself; fold it into any future MCP input
  pass.

## Not audited
